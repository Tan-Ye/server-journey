## D2 · 阶段 0 · 3h

目标：把订单状态机写成可执行的规格 —— 转移表（从状态 → 到状态）+ 触发者 + 前置条件 + Mermaid 状态图，合法转移只在一处定义。

实际耗时：（待填）

产出物：`projects/trade-core/docs/02-state-machine.md` —— 9 个状态 + 13 个事件 + **24 条合法转移（T1–T18b）** + 14 条被拒绝转移、三道幂等闸门、转移副作用清单、Rust 侧实现映射、**第 10 节【需人工介入】场景清单（11 项）**。`01-usecases.md` 同步至 v3：新增**用例 6 · 撤销退款申请**、端点清单 15 → 16、实现范围补上「一切人工介入功能都不做」。

卡点：

- **Mermaid 图渲染失败**：状态标签里用了半角分号 `;`，Mermaid 把它当语句分隔符导致整图解析失败。改成 `state "描述" as ID` 的写法（描述里不放 `;`）后正常。
- **`REFUNDING → REFUNDED` 是多条边合一个终点**：「钱退成功」（支付方回调）和「货到仓」（退货入库）哪个先到都可能，拆成 T14/T14a/T15/T15a/T16/T16a/T16b 七条边覆盖全部到达顺序，其中两个是**自环**（状态不变、只补记库存）。
- **`next_status` 签名要扩**：分岔条件（退货项是否在途、申请退款前的状态、钱是否已退、货是否到仓）都不在 `OrderStatus` 里，需加第三个纯数据参数 `TransitionCtx`。不能退化成在 Service 层用 `if` 判断终点，否则「合法转移只在一处定义」就破了。
- **撤销退款的终点是动态的**：要回到「申请退款之前的状态」，所以必须新增 `order_items.refund_from_status` 字段 —— 没有它就无法实现撤销。这是本用例对 D4 表结构提出的硬要求。
- **撤销时反向预占可能失败**（库存已被别人买走）：整个操作必须回滚、保持 `REFUNDING`，绝不允许把 `available` 扣成负数，也不允许「状态退了库存没退」。
- **人工介入的边界**：项目不实现工单/审批流/人工改状态接口，统一约定为「停下来 + 落库 + 告警 + 打标注」。已登记 11 个场景，涉及钱已退出后撤销、退款重试超限、金额不符、延迟回调、退货超期未入库等。
- **`DELIVERY_CONFIRMED` 不区分收下还是拒收**：拒收也先入 `DELIVERED` 再走退货，比现实多绕一步；好处是所有退货场景共用一条路径，不为拒收单独开边。
- **对支付方与对用户要区别对待**：状态不匹配时，支付方回调必须返回 200（否则无限重推），差异落 `payment_events.status = IGNORED`；对用户的手动操作才返回 409。

目标：定义 8–12 个端点的 API 契约（路径、方法、请求/响应字段、状态码）+ 统一错误码规范。

实际耗时：（待填）

产出物：`projects/trade-core/docs/03-api-contract.md` —— **`///` 硬约定**（状态码/错误码/常量必须带文档注释，附 `OrderStatus` 与 `ErrorCode` 的完整 Rust 写法）、通用约定（分金额/时间/分页/幂等键）、统一响应包体（含 `retryable` 与 `manual_intervention`）、HTTP 状态码规范（11 个）、**错误码总表 8 类 25 个**、枚举 `///` 清单、**常量清单 14 个**、16 个端点逐个契约、OpenAPI/TS 生成路径。

卡点：

- **错误码要拆三个维度**：无论怎么归类，每个错误码都得同时回答「数字码（前端 switch）」「字符串码（人看+检索）」「HTTP 状态码」，再加上「能否重试」与「是否需人工介入」。塞进响应体后前端才能不猜。
- **回调的状态不匹配必须返回 200**：否则支付方无限重推。这条与「错误就要报错」的直觉相反，是 DoD #3 的协议前提。
- **`202` 只给退款申请**：钱没退、结果由回调决定 —— 不能拿 `202` 当「我收下了但还没处理」的偷懒响应。
- **只暴露 `available`**：`reserved`/`in_transit`/`damaged` 是内部库存口径，暴露等于泄露经营数据。
- **`///` 不是额外负担**：`utoipa` 直接把 `///` 写进 OpenAPI 的 description，DoD #5 的文档质量完全取决于它。

### 追加 · 文档校验脚本 `tools/validate.ps1`

D2/D3 两轮自检共发现 17 处不一致，全是「人眼扫不出来但会让写代码的人踩坑」的类型。为把这类错误机械化，写了 `tools/validate.ps1`。

**能力边界（重要，别误信）**：脚本只兜机械错误 —— 数量声称 vs 实际、条目重复、编号跳号、引用不存在、跨文档名称不一致、Mermaid 语法、编码损坏、表格串列与缺空行。**它查不出**：内容本身写错（如把 400 的码写成 409，只要两张表一致就认为没问题）、该有的东西根本没写、设计决策之间的语义矛盾、默认值是否合理。语义正确性仍靠人眼。

**脚本抓出的真实错误**（人眼漏掉的）：被拒绝转移表实际 14 条，我在标题写了「共 13 条」。

**关于 `///` 纪律的连带发现**：`utoipa` 会把 `///` 直接写进 OpenAPI 的 description，所以 §1 的 `///` 硬约定不是额外负担，而是 DoD #5「契约完整」的质量来源。校验脚本目前只能查「`pub const` 前有没有 `///`」，查不了 `///` 写得对不对 —— 后者仍需人眼。

### 追加 · 把校验脚本砍到只剩分工内的功能

第一版脚本写了 469 行 / 40 项检查，但**其中一大块复杂度是在为「通用量词匹配」服务**，为此连续踩了 5 个坑、反复调试多轮。这段投入是纯浪费 —— 校验本该省时间，结果先花掉了一堆时间。

**砍法**：只保留分工里的四件事（数量核对 / 引用完整 / 结构完整 / 硬约定），删掉一切不属于它的：待产出文档的 WARN 豁免、与其他工具重叠的指标渲染统计、调试脚手架。375 行 / 35 项检查。

**砍掉后的意外收获**：删掉「未产出文档算 WARN 不算 FAIL」这条豁免后，脚本立刻报出 `04-dod.md` 死链（`02`、`03` 都把它写成下游但文件不存在）。**那条豁免等于让脚本替我说谎**。补上 `04-dod.md` 后校验转全绿 —— 也就是说，砍功能反而让它多抓到一个真问题。

**留下的 5 个坑（写进脚本注释，避免重复踩）**：
1. 章节范围必须限定到二级标题，且**同一章节里必须再精确取一张表**（否则状态集合表会把订单项聚合表一起数进来）；
2. PowerShell 字符串里反引号是转义符，正则里的 `` ` `` 必须用 `[char]0x60` 取；
3. `return , $arr` 会把数组包成单元素数组，调用方 `@()` 展不平 → `-contains` 比的是数组本身；
4. **不做通用量词归一化**，每个检查写死精确正则（中文写法混用会连环踩「正则元字符」「捕获组冲突」「共字位置」）；
5. `^\| 闸门` 会把**表头行**也数进去 → 必须写成 `^\| 闸门 [0-9]`。

**一条可复用的经验**：校验工具的复杂度要跟着「它能查的那一类错误」走。凡是需要为「兼容文档的十种写法」而写的代码，最后都会变成新的维护负担。

### 追加 · 脚本跑完后的人眼复核（三份文档各过一遍）

脚本全过后我又逐份读了一遍，**又发现 12 处问题 —— 全部是脚本查不出的类型**。这印证了一个判断：脚本只能兜「机械一致」，语义正确性必须人眼。

**语义矛盾类（最值钱的 4 处）**

1. **`GET /orders/{id}` 的越权策略自相矛盾**：§5.1 的错误码写「订单不存在**或不属于当前用户**」，§8.1 却写「他人订单返回 403」。两处措辞都对，合起来冲突。**改为统一 404** —— 若「他人订单」给 403、「不存在」给 404，攻击者能用响应差异探测订单是否存在。
2. **退款回调被写进了「支付成功」的流程**：用例 2 第 6 步无条件 `SET status='PAID' WHERE status='PENDING_PAYMENT'`，但同章 B5 又说 `REFUND_SUCCESS` 要驱动 `REFUNDED`。**补成按 `result` 分三种条件更新**（`PAY_SUCCESS` / `PAY_FAILED` / `REFUND_SUCCESS` 各自的 WHERE 与副作用都不同）。
3. **两个退款状态枚举同名**：`refunds.status` 与 `order_items.refund_status` 都叫 `RefundStatus` —— Rust 里一个模块不能有两个同名类型。**拆成 `RefundRecordStatus` 与 `OrderItemRefundStatus`**。
4. **错误码顺序与语义冲突**：`AMOUNT_MISMATCH` 编到 40925，却排在 40924「终态拒绝」之前，破坏「编号随分配递增」。**改为 40926**（40925 废弃不复用）。

**业务逻辑错误（3 处）**

5. **退货超期后「自动触发」是错的**：用例 5 第 3 路原写「或调度器在 `AUTO_RETURN_DAYS` 后自动触发」—— 用户根本没寄回货，自动退款等于白送。**改为超期只告警、打【需人工介入】#5**。
6. **重复申请退款的拦截条件过宽**：原写 `refund_status != NONE`，会把 `REVOKED`（撤销过的）也拦掉 —— 但撤销的语义正是「可以重新申请」。**改为按状态分辨**：`REFUNDING`/`PARTIALLY_REFUNDED` → 40931；`REFUNDED` → 40924。
7. **`mock-success` 的状态不匹配返回 409 是错的**：它自称走「同一条回调链路」，那状态不匹配就该跟真实回调一样返回 200 + 落 `IGNORED`。

**遗漏与表述（5 处）**

8. `04-dod.md` 是唯一未产出文档，但 §10 已把它写成下游 —— 属正常，产出后 WARN 消失。
9. 用例 3 的 B6 写「403」与人眼复核后的统一 404 策略冲突，已改。
10. 用例 2 主流程漏了「只有 `PAY_SUCCESS` 才进入发货推进」，补齐。
11. `02-state-machine.md` §5 的「结果」列把 HTTP 状态码和文字混在一列（`409 ORDER_NOT_...` 与「拒绝 —— 钱已收」并列），且漏了 3 条契约文档里有的拒绝情形（`REFUND_NOT_REVOCABLE`、`ORDER_ALREADY_FINAL`、`AMOUNT_MISMATCH`）。**重写为 R1–R18，新增独立的「HTTP + 错误码」列**。
12. §6 的表格紧贴上一行文字（无空行）会导致表格不渲染；§10 标题同样问题。已修。

**这一轮脚本还抓到我自己的改动破坏的一致性**：把 §5 表头从 `| 意图 |` 改成 `| # | 意图 |` 后，脚本立刻报「被拒绝转移条数一致（实际 0）」—— 说明它确实能兜住「改了结构没同步校验逻辑」这类问题。改成按 `R\d+` 编号数行，比按列名稳。

## D4 · 阶段 0 · 3h

目标：DoD 清单落到可执行的验证方式 + 三个难点（不超卖 / 幂等 / 超时取消）的初步方案假设 + 核心表字段草案。

实际耗时：（待填）

产出物：`projects/trade-core/docs/04-dod.md` —— **DoD 九条的验证方式表**（每条给出可执行命令 + 断言 + 主要卡点）、**三个难点的方案假设**（每条带「怎么证伪」列）、**七张表字段草案**（orders / order_items / stock / payments / payment_events / refunds / idempotency_keys，含类型、约束、索引、外加 ER 图）、交给阶段 3 的 5 项待办。

卡点：

- **DoD 必须写成「一条命令 + 一个断言」**，否则 W8 压测时会出现「感觉没问题」这种结论。九条里 #1 #3 #4 都依赖并发脚本，得先有 k6。
- **`CHECK (available >= 0)` 这类数据库约束要当第一道防线**：应用层漏判时让数据库直接拒绝，比在日志里发现负库存早得多。约束要跟迁移脚本一起上，别事后补。
- **七张表里有三处「故意反范式」**：`order_items` 存商品名称与价格快照（商品改名/下架不影响历史订单）、`product_id` 不建外键（下架不该阻挡退款）、`damaged` 独立成栏而不并入某处（残次品不可售是硬语义）。
- **一个刻意不做的优化**：v1 不加 Redis 预扣库存，全靠数据库条件更新。理由是先把「不超卖」的正确性钉死；若 W8 压测扛不住再评估 —— 但那时要先证明是「慢」而不是「错」。
- **状态枚举类型名必须区分**：`orders.status` 用 `OrderStatus`，`refunds.status` 用 `RefundRecordStatus`，`order_items.refund_status` 用 `OrderItemRefundStatus`。两个退款枚举同名会让 Rust 编译不过（`03-api-contract.md` §6 已定为硬约定）。
- **漏了 `products` 表**（自查时被你指出）：原草案只有七张表，`order_items.product_id` 与 `stock.product_id` 指向一个不存在的表，用例里反复出现的「商品存在且 `ON_SALE`」这个前置条件也无处可查。补为八张表，「商品不上物理删除、只置 `OFF_SALE`」写进硬纪律。
- **`stock` 的粒度没说清**：它是**按商品**记账（一行 = 一个商品），不是「订单下的库存表」。订单与库存没有从属关系，下单只是从对应商品那一行借走若干件。已在两处文档里显式写明。
- **`total_inbound` 的对账等式写错了**：原来写成四栏之和 ≤ `total_inbound`，但正向签收后货已交付用户、离开四栏，差额无从解释。正确形式是 `available + reserved + in_transit + damaged + sold = total_inbound`，其中 `sold` 由订单聚合得出，**不落库**（落库就等于重复真相源）。退货入库时 `sold` 减、`available`/`damaged` 加，两侧同变，等式仍成立。
- **反范式结论也修正了**：原来写「`product_id` 不建外键」，但既然商品不允许物理删除，外键可以且应该建（`ON DELETE RESTRICT`）—— 它防的是「`stock` 里挂了不存在的商品」。真正该保留的反范式只有一条：`order_items` 存名称与价格快照，退款不 JOIN `products`。

**✅ 已解决：根因是宿主端口冲突，不是密码问题。**

真实根因：**本机已安装原生 PostgreSQL 18**（Windows 服务 `postgresql-x64-18`，`C:\Program Files\PostgreSQL\18`）**占用了宿主 5432 端口**。容器原本也发布到 5432，于是出现「两个进程抢同一端口」，宿主连接被路由到**原生实例**而不是容器 —— 那个实例自然不认识 `trade` 用户，于是报「密码认证失败」。

- 判据（决定性）：打开 `log_connections` 后复现失败连接，**容器日志里完全没有这次连接的记录**；而对照测试 `127.0.0.1:5432` 从容器内返回 `Connection refused`。请求根本没到我们的容器。
- 修法：宿主端口错开 —— Postgres `5433:5432`、Redis `6380:6379`，`.env` 与 `.env.example` 同步改。
- 修后实测：`sqlx migrate info` / `sqlx database create` 均 `exit=0` 且无输出；宿主侧 `HOST_OK_5433`；Redis `PONG`；原生 PG 18 仍在 5432 未受影响。

**走过的弯路（值得记下）**：我先入为主地把「密码认证失败」当成根因，花了大量时间在密码上 —— 写了 5 个版本的自写 SCRAM 客户端、比对 `pg_authid` 校验子、改 `lc_messages`、重设密码。这些**全部是无用功**，因为连的根本不是那个实例。

**正确的排查顺序应该是**（三步就能定位）：
1. **开 `log_connections`，复现失败，看服务端有没有记录** —— 没有记录就说明请求没到，与密码无关
2. **`netstat` 看端口有几个监听者** —— 发现两个进程抢 5432
3. **查已安装程序与服务** —— 找到原生 PostgreSQL 18

这三步花了不到 5 分钟。而我实际走的路径花了几小时。**教训：报错信息会骗人（「密码错误」其实是「连错实例」），但「请求有没有到达服务端」永远是硬事实，应该第一个查。**

其他卡点：

1. **沙箱不允许访问命名管道**：`docker` 命令由我执行时每次都要一次权限放宽（与 `git push` 走 SSH 同根因）。这一轮排障因此批了十几次授权，**建议容器相关操作一律由我在你终端给出命令、你来执行**。
2. **WSL 安装踩坑**：`wsl --install` 会连带下载 **500MB+ 的 Ubuntu 发行版**，慢在那第三个包。而 **Docker Desktop 根本不需要发行版**（它自建 `docker-desktop`）。正确做法是 `wsl --install --no-distribution`，或 Win11 专业版直接用 Hyper-V 后端。
3. **`sqlx-cli` 安装必须带 flag**：`--no-default-features --features postgres,rustls --locked`（默认特性会拉 MySQL/SQLite 并依赖 OpenSSL，Windows 上容易编译失败），且**要求 rustc ≥ 1.94**，所以要先 `rustup update stable`。
4. **中文 locale 会导致 sqlx 报错完全不可读**：服务端发中文错误消息时，sqlx 把它们报成 `non-UTF-8 protocol error`，真实错误被完全掩盖。已在 compose 里钉住 `LANG`/`LC_ALL=C.UTF-8`。
5. **`SHOW lc_collate` 在 PG 16+ 已失效**（改为 per-database 属性），要从 `pg_database` 查。
6. **自写协议客户端的教训**：为了抓真实错误我手搓了 SCRAM 客户端，期间踩了我自己的 4 个 bug（`rd` 撞 PowerShell 内置别名、`AddRange` 类型转换失败、SASL 首包多插一个 `0`、大端/小端读反）。**涉及密码认证的问题，先用现成客户端验证，不要手搓协议。**
